40: โครงงานระบบผู้ช่วยบ้านอัจฉริยะภาษาไทย (AI Smart Home Thai Assistant) ฉบับนี้ สำเร็จลุล่วงไปได้ด้วยความช่วยเหลืออย่างดียิ่งจากอาจารย์ที่ปรึกษา ที่ได้กรุณาให้คำปรึกษา แนะนำแนวทาง และตรวจสอบแก้ไขข้อบกพร่องต่าง ๆ ตลอดระยะเวลาการดำเนินโครงงาน ขอขอบพระคุณเป็นอย่างสูงไว้ ณ โอกาสนี้
41: ขอขอบคุณคณะ [ชื่อคณะ] [ชื่อมหาวิทยาลัย] ที่สนับสนุนสถานที่ อุปกรณ์ และ ทรัพยากรต่าง ๆ ที่จำเป็นต่อการดำเนินโครงงานนี้ ขอขอบคุณเจ้าหน้าที่ภาควิชา ทุกท่านที่อำนวยความสะดวกในการยืมอุปกรณ์และการใช้ห้องปฏิบัติการ รวมถึง เพื่อน ๆ ทุกคนที่ให้คำแนะนำและกำลังใจ
42: นอกจากนี้ ขอขอบคุณทีมพัฒนา Ollama, faster-whisper, Edge TTS, FastAPI และ Espressif Systems ที่พัฒนาเครื่องมือและไลบรารีที่ใช้ในโครงงานนี้
43: สุดท้ายนี้ ผู้จัดทำขอกราบขอบพระคุณบิดา มารดา และครอบครัว ที่ให้กำลังใจ และสนับสนุนด้านการศึกษาเสมอมา ประโยชน์และคุณค่าอันพึงมีจากโครงงานนี้ ผู้จัดทำขอมอบเป็นเครื่องบูชาพระคุณของบิดา มารดา ครูอาจารย์ และผู้มีพระคุณทุกท่าน

48: บทคัดย่อ
49: โครงงานนี้มีวัตถุประสงค์เพื่อพัฒนาระบบผู้ช่วยบ้านอัจฉริยะภาษาไทยที่สามารถสนทนา โต้ตอบกับผู้ใช้ด้วยภาษาไทย ควบคุมอุปกรณ์ไฟฟ้าภายในบ้าน อ่านค่าจากเซนเซอร์ และให้ข้อมูลภายนอกผ่าน API ได้แบบเรียลไทม์ โดยใช้บอร์ด ESP32-S3 เป็นตัวควบคุม อุปกรณ์และเซนเซอร์ เชื่อมต่อกับเซิร์ฟเวอร์ภายในเครื่องที่ใช้ FastAPI และ Local LLM ผ่าน Ollama โดยเดโมปัจจุบันใช้ Gemma 4 E2B เป็นโมเดลหลัก และยังรองรับ Typhoon 2 8B เป็นโมเดลทางเลือกสำหรับการประมวลผลภาษาธรรมชาติ
50: ระบบประกอบด้วย 3 ส่วนหลัก ได้แก่ (1) เซิร์ฟเวอร์ภายในเครื่องที่ทำหน้าที่ รับคำถาม วิเคราะห์เจตนา (Intent Classification) เรียกข้อมูลจาก API ภายนอก และสร้างคำตอบด้วย AI (2) Web UI Dashboard สำหรับสนทนาผ่านเบราว์เซอร์ พร้อมแสดงสถานะเซนเซอร์และการควบคุมรีเลย์แบบ Real-time และ (3) บอร์ด ESP32-S3 สองตัว โดยตัวแรกเป็น Control Node ที่เขียนด้วย MicroPython สำหรับอ่านค่า DHT22, PIR Motion และควบคุม Relay Module ส่วนตัวที่สอง เป็น Voice Node ที่ใช้ ESP-IDF สำหรับการรับเสียงจากไมโครโฟน INMP441 และเล่นเสียงตอบกลับผ่าน MAX98357A + ลำโพง
51: ระบบออกแบบให้แกนหลักของการสนทนาและการควบคุม IoT ทำงานบนเครื่อง Local โดยใช้ Local LLM ผ่าน Ollama, Thai STT (faster-whisper) และ Thai TTS ผ่าน Edge TTS เพื่อรองรับการสนทนาด้วยเสียงภาษาไทยอย่างสมบูรณ์ นอกจากนี้ยังมีกลไก Intent Router แบบ Rule-based เพื่อเพิ่มความเร็วในการตอบสนองสำหรับ คำสั่งควบคุมอุปกรณ์และคำถามทั่วไป
52: ผลการดำเนินงานพบว่าระบบสามารถทำงานได้ตามวัตถุประสงค์หลักสำหรับการเดโม โดยยังมีบางส่วนที่ควรพัฒนาต่อสำหรับการใช้งานจริงระยะยาว เซิร์ฟเวอร์สามารถตอบคำถามภาษาไทยผ่านการพิมพ์และการพูดได้อย่างถูกต้อง สามารถควบคุมรีเลย์เปิด-ปิดอุปกรณ์ไฟฟ้า แสดงค่าอุณหภูมิและความชื้นแบบ Real-time และให้ข้อมูลสภาพอากาศ ข่าวสาร การจราจร และการนำทางผ่าน API ภายนอกได้ Voice Node สามารถรับคำสั่งเสียงผ่านการตรวจจับคำปลุก (Wake Word) และเล่นเสียงตอบกลับผ่านลำโพงได้ อีกทั้งระบบยังมี Dashboard ที่แสดงสถานะต่าง ๆ ได้อย่างครบถ้วน

54: Abstract
55: This project aims to develop a Thai language smart home assistant system capable of conversing with users in Thai, controlling home electrical appliances, reading sensor data, and providing real-time external information through APIs. The system uses ESP32-S3 microcontrollers as control and voice nodes, connected to a local FastAPI server running a local LLM through Ollama. The current demo uses Gemma 4 E2B as the primary model while Typhoon 2 8B remains an optional alternative.
56: The system consists of three main components: (1) a local server that handles question analysis, intent classification, external API calls, and AI response generation, (2) a Web UI Dashboard for browser-based conversation with real-time sensor data and relay control display, and (3) two ESP32-S3 boards - a Control Node using MicroPython for DHT22 temperature/humidity sensor, PIR motion sensor, and relay control, and a Voice Node using ESP-IDF for INMP441 microphone input and MAX98357A speaker output.
57: The core chat and IoT control pipeline is designed to run locally using a Local LLM via Ollama, Thai STT (faster-whisper), and Thai TTS via Edge TTS for complete Thai voice interaction support. A rule-based Intent Router is implemented to improve response speed for device control commands and common queries.
58: Engineering test results show the system meets the main demo objectives, while some production-level items such as long-term persistence and native ESP-SR wake word tuning remain future work. The server can accurately respond to Thai questions through both text and voice input, control relays for electrical appliances, display real-time temperature and humidity readings, and provide weather, news, traffic, and navigation information through external APIs. The Voice Node can receive voice commands via wake word detection and play audio responses through the speaker. The Dashboard displays comprehensive system status information.

207: 1.1 ที่มาและความสำคัญ
208: ในปัจจุบันเทคโนโลยีปัญญาประดิษฐ์ (Artificial Intelligence: AI) และอินเทอร์เน็ตของสรรพสิ่ง (Internet of Things: IoT) ได้เข้ามามีบทบาทสำคัญในชีวิตประจำวันของมนุษย์มากขึ้น โดยเฉพาะ อย่างยิ่งในด้านระบบบ้านอัจฉริยะ (Smart Home) ที่ช่วยอำนวยความสะดวก เพิ่มความปลอดภัย และประหยัดพลังงานในการดำรงชีวิต อย่างไรก็ตาม ระบบบ้านอัจฉริยะที่มีอยู่ในท้องตลาดส่วนใหญ่ มีข้อจำกัดที่สำคัญหลายประการ
209: ประการแรก ระบบบ้านอัจฉริยะส่วนใหญ่มักเป็นระบบที่ต้องพึ่งพาบริการคลาวด์ (Cloud Computing) ทำให้ข้อมูลการใช้งานและข้อมูลภายในบ้านต้องถูกส่งไปประมวลผลบนเซิร์ฟเวอร์ภายนอก ซึ่งอาจมีความเสี่ยงด้านความเป็นส่วนตัวของข้อมูล (Data Privacy) และความปลอดภัยของข้อมูล (Data Security) นอกจากนี้ยังมีปัญหาความล่าช้าในการสื่อสาร (Latency) โดยเฉพาะเมื่อ อินเทอร์เน็ตไม่เสถียร
210: ประการที่สอง ระบบบ้านอัจฉริยะส่วนใหญ่รองรับเฉพาะภาษาอังกฤษหรือภาษาจีนเป็นหลัก ทำให้ผู้ใช้ที่สื่อสารด้วยภาษาไทยอาจประสบปัญหาในการใช้งาน เนื่องจากระบบไม่เข้าใจ ภาษาไทยอย่างเป็นธรรมชาติ ส่งผลให้ประสบการณ์การใช้งานไม่ราบรื่นเท่าที่ควร
211: ประการที่สาม การพัฒนาระบบบ้านอัจฉริยะที่สามารถสนทนาภาษาไทยได้นั้นต้องอาศัยโมเดลภาษาขนาดใหญ่ (Large Language Model: LLM) ที่รองรับภาษาไทยได้ดี ซึ่งปัจจุบันสามารถรันในเครื่องได้ผ่าน Ollama เช่น Gemma, Typhoon และโมเดลตระกูลอื่น ๆ ทำให้ระบบลดการพึ่งพา Cloud LLM ได้มากขึ้น

257: 2.1 แนวคิดและทฤษฎีที่เกี่ยวข้อง
258: 2.1.1 ปัญญาประดิษฐ์ (Artificial Intelligence)
259: ปัญญาประดิษฐ์ (AI) เป็นสาขาหนึ่งของวิทยาการคอมพิวเตอร์ที่มุ่งสร้างระบบที่สามารถ เลียนแบบความฉลาดของมนุษย์ เช่น การเรียนรู้ การให้เหตุผล การแก้ปัญหา และการเข้าใจภาษา AI แบ่งออกเป็นหลายประเภท ตั้งแต่นarrow AI ที่ทำงานเฉพาะด้าน ไปจนถึง General AI ที่สามารถทำงานได้หลากหลาย ในโครงงานนี้ใช้ Narrow AI ในรูปแบบของ Large Language Model (LLM) และ Speech Recognition
260: 2.1.2 การประมวลผลภาษาธรรมชาติ (Natural Language Processing)
261: NLP เป็นสาขาย่อยของ AI ที่เกี่ยวข้องกับปฏิสัมพันธ์ระหว่างคอมพิวเตอร์และภาษามนุษย์ ภาษาไทยมีลักษณะเฉพาะที่ท้าทายสำหรับ NLP ได้แก่ การไม่มีการเว้นวรรคระหว่างคำ (Word Boundary Detection) การมีวรรณยุกต์ (Tone Marks) ที่เปลี่ยนความหมายของคำ และคำพ้องเสียง (Homophones) จำนวนมาก ระบบนี้จึงใช้แนวทาง Local LLM ร่วมกับ Intent Router และ domain correction เพื่อช่วยให้การตอบภาษาไทยในบริบทบ้านอัจฉริยะมีความแม่นยำขึ้น
262: 2.1.2.1 การจำแนกเจตนา (Intent Classification)
263: Intent Classification เป็นกระบวนการระบุเจตนาหรือวัตถุประสงค์ของผู้ใช้จากข้อความ ที่ป้อนเข้าไป ในโครงงานนี้ใช้การจำแนกแบบ Rule-based โดยใช้ Keyword Matching ร่วมกับ Regular Expression เพื่อแบ่งประเภทคำถามออกเป็น 10 ประเภท ได้แก่ device_control, weather_query, news_query, traffic_query, navigation_query, sensor_query, line_send_request, news_detail_query, system_status และ general_chat
264: 2.1.3 อินเทอร์เน็ตของสรรพสิ่ง (Internet of Things: IoT)
265: IoT เป็นแนวคิดที่ให้อุปกรณ์ต่าง ๆ สามารถเชื่อมต่อและสื่อสารกันผ่านเครือข่ายอินเทอร์เน็ต สถาปัตยกรรม IoT ทั่วไปประกอบด้วย 4 ชั้น: (1) Device Layer - อุปกรณ์ฮาร์ดแวร์และเซนเซอร์ (2) Network Layer - การเชื่อมต่อและโปรโตคอลการสื่อสาร (3) Middleware Layer - การจัดการ ข้อมูลและการประมวลผล (4) Application Layer - แอปพลิเคชันสำหรับผู้ใช้

ในโครงงานนี้ใช้สถาปัตยกรรมแบบ Local IoT หรือ Edge Computing โดยข้อมูลจากเซนเซอร์ ถูกส่งไปยังเซิร์ฟเวอร์ภายในเครื่องผ่าน Wi-Fi ซึ่งช่วยลด Latency และเพิ่มความปลอดภัย ของข้อมูล เนื่องจากข้อมูลไม่ต้องส่งออกไปยังคลาวด์
266: 2.1.4 การรู้จำเสียงพูด (Speech-to-Text: STT)
267: STT เป็นกระบวนการแปลงสัญญาณเสียงพูดเป็นข้อความ โดยทั่วไปประกอบด้วยขั้นตอน: (1) การรับสัญญาณเสียงผ่านไมโครโฟน (2) การแปลงสัญญาณอนาล็อกเป็นดิจิทัล (ADC) (3) การแยกคุณลักษณะของเสียง (Feature Extraction) เช่น MFCC (4) การจับคู่กับ รูปแบบเสียงในฐานข้อมูล (Acoustic Model) (5) การถอดความ (Language Model) และ (6) การปรับปรุงความถูกต้อง (Post-processing)

โครงงานนี้ใช้ faster-whisper รุ่น small ซึ่งใช้สถาปัตยกรรม Encoder-Decoder Transformer มีความแม่นยำสูงและทำงานบน CPU ได้ รองรับภาษาไทยและมี VAD (Voice Activity Detection) ในตัว
268: 2.1.5 การสังเคราะห์เสียงพูด (Text-to-Speech: TTS)
269: TTS เป็นกระบวนการแปลงข้อความเป็นเสียงพูด ปัจจุบันมีหลายแนวทาง ได้แก่ Concatenative TTS ที่นำหน่วยเสียงที่บันทึกไว้มาต่อกัน, Parametric TTS ที่ใช้ แบบจำลองทางคณิตศาสตร์สร้างเสียง และ Neural TTS ที่ใช้ Deep Learning ซึ่งให้ เสียงที่เป็นธรรมชาติที่สุด โครงงานนี้ใช้ Edge TTS ซึ่งเป็น Neural TTS ของ Microsoft ที่รองรับภาษาไทยด้วยเสียง th-TH-PremwadeeNeural
270: 2.2 เทคโนโลยีและอุปกรณ์ที่เกี่ยวข้อง
271: 2.2.1 บอร์ด ESP32-S3
272: ESP32-S3 เป็นไมโครคอนโทรลเลอร์จาก Espressif Systems ที่ออกแบบมาสำหรับ งาน AIoT โดยเฉพาะ มีคุณสมบัติดังนี้

- CPU: Xtensa LX7 Dual-Core 32-bit สูงสุด 240 MHz
- RAM: 512 KB SRAM + สูงสุด 8 MB PSRAM (รุ่น N16R8)
- Flash: สูงสุด 16 MB
- Wireless: Wi-Fi 802.11 b/g/n + Bluetooth 5.0 LE
- Interfaces: I2S, I2C, SPI, UART, USB OTG, LCD, Camera
- AI Accelerator: Vector instructions สำหรับงาน Neural Network

จุดเด่นของ ESP32-S3 ที่สำคัญต่อโครงงานนี้คือ I2S Interface ซึ่งรองรับการเชื่อมต่อ ไมโครโฟนดิจิทัล (INMP441) และแอมป์ลำโพง (MAX98357A) ได้โดยตรง และมี PSRAM ขนาดใหญ่พอสำหรับบัฟเฟอร์เสียง

277: 2.2.2 FastAPI Framework
278: FastAPI เป็นเว็บเฟรมเวิร์กภาษา Python ที่ได้รับความนิยมสำหรับสร้าง REST API มีจุดเด่นด้านประสิทธิภาพสูงด้วยการรองรับ Asynchronous Programming ผ่าน Python asyncio มีระบบ Type Validation ด้วย Pydantic สร้างเอกสาร API อัตโนมัติด้วย Swagger UI และ ReDoc และรองรับ WebSocket สำหรับการสื่อสาร แบบ Real-time

เหตุผลที่เลือก FastAPI: (1) ความเร็วสูงเทียบเท่า Go และ Node.js (2) การตรวจสอบชนิดข้อมูลอัตโนมัติช่วยลด Bug (3) รองรับ WebSocket สำหรับสตรีมเสียง (4) มีระบบ Dependency Injection ที่ยืดหยุ่น (5) ชุมชนขนาดใหญ่และเอกสารครบถ้วน

283: 2.2.3 Ollama และ Local LLM สำหรับภาษาไทย
284: Ollama เป็นเครื่องมือ Open-Source สำหรับรัน LLM ในเครื่องส่วนตัว รองรับ โมเดลหลากหลาย เช่น Llama, Gemma, Mistral และ Typhoon มีฟีเจอร์:
- การจัดการโมเดล: ดาวน์โหลด จัดเก็บ และสลับโมเดลได้ง่าย
- REST API: รองรับ OpenAI-compatible API
- Keep Alive: รักษาโมเดลในหน่วยความจำเพื่อลด Cold Start Latency
- Quantization: รองรับการบีบอัดโมเดล (Q4, Q8) เพื่อลดการใช้ทรัพยากร

ระบบนี้ใช้ Ollama เพื่อรัน Local LLM บนเครื่องผู้ใช้ โดยเดโมล่าสุดเลือก Gemma 4 E2B เป็นโมเดลหลักเพราะตอบสนองเร็วกว่าในเครื่องที่มีทรัพยากรจำกัด ส่วน Typhoon 2 8B ยังเป็นโมเดลทางเลือกสำหรับงานภาษาไทยที่ต้องการเปรียบเทียบคุณภาพคำตอบ ทั้งสองแนวทางช่วยให้ส่วนสนทนาหลักทำงานได้โดยไม่ต้องพึ่ง API ของ LLM ภายนอก

290: 2.2.4 Faster-Whisper
291: Faster-Whisper เป็นไลบรารีถอดเสียงภาษาไทยที่พัฒนาโดย OpenAI ใช้สถาปัตยกรรม Encoder-Decoder Transformer มีความแม่นยำสูงและทำงานได้เร็วกว่า Whisher เดิมถึง 4 เท่าด้วย CTranslate2 รุ่น small (244 MB) สามารถรันบน CPU ได้ โดยใช้ INT8 Quantization รองรับ VAD Filter ที่ใช้ Silero VAD และสามารถตรวจจับภาษาได้อัตโนมัติ
292: การตั้งค่าเพิ่มเติมของ faster-whisper ประกอบด้วย beam_size = 5 (ขนาด Beam Search สำหรับถอดรหัส), vad_filter = True (กรองเฉพาะส่วนที่มีเสียงพูด), audio_normalize = True (ปรับระดับเสียงอัตโนมัติด้วย target_peak = 0.82 และ max_gain = 3.0), domain_corrections = True (แก้ไขคำศัพท์เฉพาะทางภาษาไทย) และ initial_prompt ที่มีคำศัพท์พบบ่อย เช่น ข่าว อากาศ ฝน รถติด เปิดไฟ ปิดไฟ เพื่อเพิ่มความแม่นยำในการถอดเสียงภาษาไทย
293: 2.2.5 Edge TTS
294: Edge TTS เป็นไลบรารีภาษา Python สำหรับเข้าถึงบริการ TTS ของ Microsoft Edge โดยไม่ต้องพึ่งพา API Key รองรับเสียงมากกว่า 400 เสียงใน 100 ภาษา สำหรับภาษาไทย มีเสียง th-TH-PremwadeeNeural (ผู้หญิง) และ th-TH-NiwatNeural (ผู้ชาย) ให้เสียงที่เป็นธรรมชาติ มีการเน้นคำและระดับเสียงที่เหมาะสม
295: 2.2.6 เซนเซอร์ DHT22
296: DHT22 (AM2302) เป็นเซนเซอร์วัดอุณหภูมิและความชื้น มีคุณสมบัติ:
- วัดอุณหภูมิได้ -40 ถึง 80°C (±0.5°C)
- วัดความชื้นได้ 0-100% RH (±2-5% RH)
- Sampling Rate: 0.5 Hz (ทุก 2 วินาที)
- แรงดันไฟ: 3.3-6V DC
- การสื่อสาร: 1-Wire Protocol

DHT22 ถูกเลือกใช้เพราะมีความแม่นยำสูงกว่า DHT11 และมีราคาที่เหมาะสม

563: 3.3.1 สถาปัตยกรรมระบบ (System Architecture)
564: ระบบถูกออกแบบแบบ 3-Tier Architecture ประกอบด้วย 3 ชั้นหลัก ได้แก่ Presentation Layer, Server Layer และ IoT Layer
565: 
566: 
567: รูป: แผนภาพสถาปัตยกรรมระบบโดยรวม 3 ชั้น (System Architecture Diagram)
568: 
569: รายละเอียดแต่ละชั้น:

1) Presentation Layer: Web UI Dashboard ที่พัฒนาด้วย HTML5 + CSS3 + Vanilla JS รันบนเบราว์เซอร์ รองรับทั้ง Chrome และ Edge มีฟีเจอร์ Push-to-Talk และ Wake Word ผ่าน Web Speech API

2) Server Layer: เซิร์ฟเวอร์ FastAPI ที่เป็นสมองกลางของระบบ ประกอบด้วย:
   - Intent Router: จำแนกประเภทคำถาม 9 ประเภท
   - Chat Service: จัดการการสนทนาทั้งหมด
   - LLM Manager: เชื่อมต่อ Ollama API
   - Device Control: จัดการคำสั่งควบคุมอุปกรณ์
   - Voice Node Manager: จัดการ Voice Node State
   - External API Services: Weather, News, Traffic, Navigation
   - TTS/STT Services: สังเคราะห์และรู้จำเสียง

3) IoT Layer: ประกอบด้วย:
   - Control Node (ESP32-S3 + MicroPython): อ่าน DHT22, PIR, ควบคุม Relay
   - Voice Node (ESP32-S3 + ESP-IDF): รับเสียง INMP441, เล่นเสียง MAX98357A

685: 3.3.7 การออกแบบ Streaming Audio Pipeline
686: นอกเหนือจากการอัปโหลดไฟล์เสียงแบบ HTTP Multipart แล้ว ระบบยังได้ออกแบบ และพัฒนาการรับส่งเสียงแบบ Real-time ผ่าน WebSocket Streaming สำหรับ Voice Node ESP32-S3 โดยมีหลักการทำงานดังนี้
687: เมื่อ Voice Node เปิดการเชื่อมต่อ WebSocket ไปยัง endpoint /voice-node/audio/stream ESP32 จะเริ่มส่งข้อมูลเสียงแบบ PCM 16-bit 16 kHz เป็นชิ้น ๆ (chunks) ไปยังเซิร์ฟเวอร์ โดยเซิร์ฟเวอร์จะเก็บข้อมูลใน PCM buffer และวิเคราะห์สถานะการพูดแบบ Real-time
688: ขั้นตอนการประมวลผล Streaming Audio:
689:   Voice Node เปิด WebSocket ไปยัง /voice-node/audio/stream พร้อมส่ง device_id, sample_rate, channels, bits_per_sample
690:   เซิร์ฟเวอร์ตอบรับการเชื่อมต่อและเริ่มรับ PCM chunks จากบอร์ด
691:   ทุก chunk ที่ได้รับจะถูกวิเคราะห์หาค่า Peak Ratio และ RMS Ratio เพื่อตรวจสอบว่ามีเสียงพูดหรือไม่
692:   หากไม่มีเสียงพูด (RMS < vad_rms_threshold) จะนับเป็น silence frame
693:   หากมีเสียงพูดต่อเนื่องเกิน VAD_START_FRAMES (3 frames) จะเริ่มนับ utterance
694:   เมื่อสิ้นสุดการพูด (silence เกิน VAD_END_FRAMES = 10 frames) หรือ WebSocket ปิด ระบบจะตัดเสียงเฉพาะส่วนที่พูด
695:   นำ PCM ที่ตัดแล้วเข้า prepare_pcm16_for_stt() เพื่อ Trim silence ขอบ, Normalize Gain, แล้วห่อเป็น WAV
696:   WAV ที่ได้จะถูกส่งเข้า STT (faster-whisper) เพื่อถอดข้อความภาษาไทย
697: ·  ข้อความที่ได้จะถูกส่งให้ Local LLM ผ่าน Ollama สร้างคำตอบ
698:   TTS (Edge TTS) สังเคราะห์คำตอบเป็นเสียง WAV 24 kHz
699:   เซิร์ฟเวอร์ queue คำสั่ง play_audio ให้ Voice Node polling ไปเล่น
700: การออกแบบนี้ช่วยลด Latency เมื่อเทียบกับ HTTP Upload แบบเดิม เนื่องจากไม่ต้องรอให้ บันทึกเสียงทั้งหมดก่อนส่ง และเซิร์ฟเวอร์สามารถเริ่มประมวลผลได้ทันทีที่ผู้ใช้พูดจบ โดยมีพารามิเตอร์ปรับแต่งได้ผ่าน Config: vad_rms_threshold (ค่าเริ่มต้น 0.025), vad_start_frames (3), vad_end_frames (10), trim_padding_ms (250)
701: พารามิเตอร์ VAD สำหรับ Streaming Audio Pipeline ประกอบด้วย vad_rms_threshold = 0.025 (เกณฑ์ RMS สำหรับแยกเสียงพูด/ silence), vad_start_frames = 3 frames (จำนวน frames ที่ต้องมีเสียงก่อนเริ่มต้น utterance), vad_end_frames = 10 frames (จำนวน silence frames ก่อนตัดว่าสิ้นสุด utterance), และ trim_padding_ms = 250 ms (padding ก่อน-หลัง utterance)

1092: การวิเคราะห์คุณภาพเสียงที่อัปโหลด (Audio Quality Metrics):
1093: ระบบวิเคราะห์คุณภาพเสียงทุกครั้งที่ Voice Node อัปโหลดเสียงผ่าน Assistant Audio Pipeline โดยใช้พารามิเตอร์ดังนี้
1094: • Peak Ratio: ค่า Peak สูงสุดของสัญญาณเสียงเทียบกับ 32767 — Clipping ถ้า ≥ 0.98
1095: • RMS Ratio: ค่า RMS เฉลี่ยของสัญญาณเมื่อเทียบกับ 32767 — Too Quiet ถ้า < 0.006
1096: • Clipping Ratio: สัดส่วนของ samples ที่เกิน 32000 — Clipped ถ้า ≥ 1%
1097: • Silence Ratio: สัดส่วนของ samples ที่เงียบ (≤ 120) — Too Quiet ถ้า > 97%
1098: • Duration: ความยาวเสียงที่บันทึก — Too Short ถ้า < 900ms

1246: faster-whisper รุ่น small มีความแม่นยำ ~80% ที่ระยะ 10-20 ซม. ซึ่งเพียงพอสำหรับการใช้งานในห้อง ควรเพิ่ม noise reduction เพื่อเพิ่มความแม่นยำ
1247: ความเสถียร:
1248: ระบบทำงานต่อเนื่อง 48 ชั่วโมงโดยไม่มีปัญหา อัตราความสำเร็จ API 99.2% ESP32 สามารถ reconnect อัตโนมัติเมื่อ Wi-Fi หลุด
1249: การใช้ทรัพยากร:
1250: เซิร์ฟเวอร์ใช้ RAM ~180 MB ส่วน Ollama ใช้ ~6 GB สำหรับโมเดล Q4 CPU Usage อยู่ในเกณฑ์ acceptable สำหรับเครื่องทั่วไป

1256: บทที่ 5
1257: สรุปผลและข้อเสนอแนะ
1258: 5.1 สรุปผลการดำเนินงาน
1259: โครงงานระบบผู้ช่วยบ้านอัจฉริยะภาษาไทย (AI Smart Home Thai Assistant) สามารถดำเนินการได้สำเร็จตามวัตถุประสงค์ที่กำหนดไว้ทุกประการ
1260: ระบบสามารถสนทนาภาษาไทยผ่าน Local LLM บน Ollama โดยคำสั่งที่เข้า fast-path เช่น อุปกรณ์ เซนเซอร์ สภาพอากาศ ข่าว และจราจรจะตอบได้เร็วกว่า ส่วนคำถามทั่วไปขึ้นกับสถานะ warmup และความยาวคำตอบของโมเดล
1261: ระบบสามารถควบคุม Relay เปิด/ปิดอุปกรณ์ไฟฟ้าผ่าน ESP32-S3 ได้อย่างถูกต้อง มี Command Lifecycle และการยืนยันผลการทำงาน
1262: ระบบสามารถอ่านค่าและแสดงผลอุณหภูมิ ความชื้น และการเคลื่อนไหวแบบ Real-time ผ่าน Dashboard ที่อัปเดตทุก 15 วินาที
1263: Voice Node ที่ใช้ ESP-IDF สามารถรับคำสั่งเสียงผ่าน Wake Word และเล่นเสียงตอบกลับผ่าน MAX98357A ได้ โดยมีอัตราสำเร็จ 80-90%
1264: ระบบสามารถบูรณาการ API ภายนอก 4 ระบบ (Weather, News, Traffic, Navigation) และทำงานได้โดยมี Cache และ Fallback ที่เหมาะสม
1265: ระบบทำงานแบบ Local ทั้งหมด รักษาความเป็นส่วนตัวของข้อมูล และทำงานต่อเนื่อง ได้มากกว่า 48 ชั่วโมงโดยไม่มีปัญหา
1266: Web UI Dashboard สามารถแสดงสถานะระบบทุกด้าน (ESP32, AI, Sensor, Voice, Device) ได้อย่างครบถ้วนและใช้งานง่าย
1267: 5.2 ปัญหาและอุปสรรค
1268: 1. ความแม่นยำของ STT สำหรับภาษาไทย
1269: faster-whisper รุ่น small มีความแม่นยำในการถอดเสียงภาษาไทยประมาณ 80% ซึ่งต่ำกว่าภาษาอังกฤษ (~95%) เนื่องจากข้อมูลการเทรนภาษาไทยมีจำกัด แนวทางแก้ไข: ใช้รุ่น medium/large, เพิ่ม Domain-specific correction, เพิ่ม noise reduction
1270: 2. Echo Feedback ใน Voice Node
1271: เสียงจากลำโพงถูกไมโครโฟนรับซ้ำ ทำให้เกิดการวนลูป แนวทางแก้ไข: เพิ่ม cooldown 800-1600 ms หลังเล่นเสียง, ปรับตำแหน่งไมค์-ลำโพง, ปิดไมค์ขณะเล่นเสียง
1272: 3. Cold Start ของ LLM
1273: Local LLM ผ่าน Ollama อาจใช้เวลาตอบรอบแรกนานกว่าปกติเมื่อโมเดลยังไม่ถูกโหลดเข้าหน่วยความจำ แนวทางแก้ไขคือ warmup อัตโนมัติ, keep-alive, health check และ fallback response ระหว่างรอ
1274: 4. API Rate Limit
1275: API ฟรีมีข้อจำกัดในการเรียกใช้ เช่น Currents API 500 calls/day แนวทางแก้ไข: Cache ผลลัพธ์ 5-10 นาที, Fallback response
1276: 5. การจัดการ Wi-Fi
1277: ESP32 อาจหลุดจากการเชื่อมต่อ Wi-Fi หากสัญญาณไม่เสถียร แนวทางแก้ไข: Auto-reconnect, Heartbeat monitoring, ใช้ Queue สำหรับคำสั่งที่ยังไม่ได้ส่ง นอกจากนี้ ESP32 ยังรายงาน Capabilities (relay_pins, sensor_pins, i2s_pins, available_pins) ให้ Dashboard แสดงผลแบบ Real-time
1278: 5.3 ข้อเสนอแนะ
1279: 5.3.1 การพัฒนาเพิ่มเติมในอนาคต
1280: Wake Word ด้วย ESP-SR WakeNet
1281: เพิ่ม WakeNet ของ Espressif สำหรับการตรวจจับคำปลุกภาษาไทย บน Voice Node โดยตรง ไม่ต้องพึ่ง Server-side Detection
1282: WebSocket Streaming Audio
1283: WebSocket Streaming Audio — ทำงานได้แล้วผ่าน /voice-node/audio/stream โดยมี PCM buffer, VAD trim, STT integration
1284: Noise Reduction (Audio Enhancement)
1285: เพิ่ม noisereduce หรือ DeepFilterNet เพื่อลด noise ก่อนเข้า STT โดยเฉพาะเสียงแอร์ พัดลม และเสียงรอบข้าง
1286: SQLite Persistence
1287: เปลี่ยนจาก In-Memory มาใช้ SQLite เพื่อบันทึกประวัติการสนทนา และข้อมูลการทำงานแบบถาวร
1288: Mobile Application
1289: พัฒนาแอปพลิเคชันมือถือสำหรับควบคุมและตรวจสอบระบบจากนอกบ้าน ผ่าน VPN หรือ Tunneling
1290: Multi-user Profiles
1291: เพิ่มระบบรู้จำผู้ใช้หลายคนด้วยเสียงและปรับการตอบสนอง ตามประวัติผู้ใช้แต่ละคน
1292: Automation Rules
1293: เพิ่มกฎอัตโนมัติ เช่น ถ้าอุณหภูมิ > 30°C และมีคนในห้อง ให้แนะนำเปิดพัดลม หรือปิดไฟอัตโนมัติเมื่อไม่มีคน
1294: 5.3.2 ข้อเสนอแนะสำหรับการนำไปใช้จริง
1295: ควรมีระบบสำรองไฟ (UPS) สำหรับเซิร์ฟเวอร์เพื่อป้องกันข้อมูลสูญหายและความเสียหายของฮาร์ดแวร์
1296: ควรใช้ฮอตสปอตมือถือเป็นอินเทอร์เน็ตสำรองในกรณีที่เน็ตบ้านล่ม
1297: ควร Warm-up โมเดล LLM ก่อนการเดโมทุกครั้ง หรือใช้ Keep-alive เพื่อรักษาโมเดลในหน่วยความจำ
1298: ควรทดสอบระบบอย่างน้อย 1 สัปดาห์ก่อนการเดโมจริง เพื่อความมั่นใจในความเสถียร
1299: ควรมี Fallback Mode เมื่อ API ภายนอกไม่พร้อม โดยใช้ข้อมูลแคชหรือตอบกลับแบบพื้นฐาน
1300: ควร Backup ไฟล์ Device Registry (.json) เป็นประจำ เพื่อป้องกันข้อมูลสูญหาย
1301: สำหรับการใช้งานจริง ควรเปลี่ยนมาใช้ Relay Module ที่มี Isolation เพื่อความปลอดภัยทางไฟฟ้า
